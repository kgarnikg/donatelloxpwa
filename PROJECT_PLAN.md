# DonatelleX — план проекта

Этот файл — единственный источник правды по тому, что сделано, что в работе
и в каком порядке двигаемся дальше. Любое новое обсуждение начинается со
сверки с этим файлом, а не с чистого листа.

## 1. Исходное ТЗ (кратко)

Платформа с подпиской для тренировок по авторской методике.

- Регистрация: email/пароль, Google, Apple
- Анкета: пол, возраст, рост/вес, цель, уровень, формат (зал/дома), дней в неделю
- Личный кабинет: дашборд, «Моя программа», питание, прогресс (вес/фото/графики), мотивационные фразы
- Каждое упражнение: название, подходы×повторения, видео-инструкция, галочка «выполнено», рабочий вес с рекомендацией на основе прошлого раза
- Подписка: после окончания — программа и питание скрываются, прогресс остаётся, предложение продлить
- Подбор программы: 8–12 готовых программ, полуавтоматический подбор по правилам, ручная коррекция тренером
- Доп.: Apple Health/Google Fit, push и Telegram-уведомления, чат поддержки через Telegram
- Технически: адаптив под мобильные, быстрая загрузка видео, GDPR, мультиязычность (ru/en/es минимум — по факту уже расширили), хостинг на GitHub

**Стратегическая цель (добавлена позже, действует как приоритет №1):**
удобное многоязычное PWA-приложение, которое в будущем легко обернуть в
полноценное нативное приложение (iOS/Android) без переписывания бизнес-логики.

## 2. Архитектура (зафиксировано, не меняем без явного решения)

- Монорепо: pnpm + Turborepo
- `apps/web` — PWA пользователя (React 19 + Vite + Tailwind)
- `apps/admin` — CMS для контента/пользователей/платежей
- `apps/landing` — маркетинговый сайт
- `packages/types`, `packages/validation`, `packages/theme` — общий код
- `supabase/` — схема БД, миграции, Edge Function для платежей
- Хостинг фронтендов — Vercel, автодеплой из GitHub

### Правило работы с БД
Каждое изменение схемы — отдельный пронумерованный файл в
`supabase/migrations/`. Файлы не редактируются задним числом — только новые.
Список миграций и их назначение веду в разделе 6.

**Фаза 3 — Платежи**
Реально протестировать хотя бы один платёжный провайдер (рекомендую
начать со Stripe — проще всего в тестовом режиме) от чекаута до
активации подписки в БД. Не забыть: применение реферальной скидки
(`pending_discount_percent`) и региональных цен из `regionPricing.ts`
при создании чекаута.

⚠️ **Важное решение по биллингу, зафиксированное заранее** (`create-checkout`
ещё не реализован — самое время заложить это с нуля, а не переделывать):
DonatelleX **не** позиционируется как подписка с автосписанием. Оплата —
разовая, за конкретный период (месяц/3/6/12), доступ действует ровно этот
срок и не продлевается сам. Landing/приложение уже переписаны под эту
формулировку ("без оплаты сейчас", "платишь один раз за период", кнопка
"Оплатить и получить доступ" вместо "Оформить подписку").
Значит, когда `create-checkout` будет писаться:
- Stripe: `mode: "payment"` (разовый платёж), НЕ `mode: "subscription"` —
  иначе Stripe сам будет пытаться списывать повторно, и текст на сайте
  разойдётся с реальным поведением
- PayPal/ЮKassa/USDT — аналогично: одноразовый платёж на сумму периода,
  без создания recurring-подписки на стороне провайдера
- Таблица `subscriptions` (название — исторически, менять не обязательно)
  под эту модель уже подходит как есть: `current_period_end` — просто
  дата, когда доступ прекращается, без автопродления
- На будущее (не в этой фазе): пуш/email-напоминание за несколько дней
  до окончания периода, чтобы пользователь мог сам купить новый —
  пользователь просил не забыть про это

## 5. Правила работы (чтобы не переделывать по 10 раз)

1. Перед началом новой фазы — сверяемся с этим файлом, что предыдущая
   реально закрыта (а не "вроде работает").
2. Любое изменение схемы БД — новый файл миграции, никогда не редактируем
   старые задним числом.
3. Перед тем как отдать код — обязательный прогон `type-check`, `lint`,
   `build` по всей монорепе by автора (уже встроено в процесс).
4. Каждый Supabase-запрос — через `toCamelCase<T>()` из `@donatellox/types`,
   без исключений (баг из Фазы 0 научил).
5. Каждая пользовательская ошибка (запрос к БД, сохранение формы) —
   обязательно показывается в интерфейсе, никогда не проглатывается молча.
6. Если фича требует внешней настройки на стороне пользователя (Supabase
   Dashboard, Google Cloud, Apple Developer) — это явно проговаривается
   ДО того, как код считается "готовым".

## 8. Важная находка: остатки старого черновика схемы в базе

27.07 обнаружено, что в реальной базе Supabase ещё до начала совместной
работы существовали таблицы `profiles`, `questionnaires` и (в старом виде)
`subscriptions` — вероятно, из самого первого черновика, который создавался
до всех миграций из этого плана. Из-за `create table if not exists`
некоторые из МОИХ таблиц (`workout_logs`, `subscriptions`) не пересоздавались
поверх этих старых версий и молча оставались с неправильной структурой —
это и было настоящей причиной ошибок `workout_logs_user_id_fkey` и
потенциальной поломки будущей системы подписок.

**Разовая рекомендация**: выполнить в SQL Editor полную сверку всех таблиц
схемы `public` на предмет других таких же расхождений:
```sql
select table_name from information_schema.tables
where table_schema = 'public' order by table_name;
```
Сравнить со списком таблиц из `0001_init_schema.sql`. Если найдутся ещё
лишние/устаревшие таблицы — прислать список, разберём так же точечно.

**Фаза 11 — Таймер отдыха в фоне (баг)** ✅ исправлено
Найдено при реальном использовании в зале: если свернуть вкладку во время
отдыха между подходами (например, ответить в мессенджере), таймер
показывал неверное время после возврата. Причина — отсчёт декрементом на
каждый тик `setInterval`, а мобильные браузеры замедляют/останавливают
таймеры у свёрнутых вкладок. Исправлено: таймер теперь считает от
абсолютной метки времени окончания (`Date.now() + секунды`), пересчитывая
оставшееся время из разницы с текущим временем на каждом рендере — плюс
принудительный пересчёт по событию `visibilitychange`, чтобы значение
обновлялось сразу при возврате на вкладку, а не ждало следующего тика.

**Дополнено:** уведомление + вибрация при завершении отдыха, пока вкладка
свёрнута. Важное ограничение платформы (не баг, не обойти кодом): прямой
`navigator.vibrate()` браузеры намеренно игнорируют у неактивных вкладок
(защита от вибрации в кармане без спроса). Обходной путь — вибрация
задаётся не напрямую, а как свойство самого браузерного уведомления
(`Notification`, показывается через `registration.showNotification()` с
опцией `vibrate`) — идёт через систему уведомлений ОС, а не голый JS
страницы, поэтому шанс сработать в фоне выше. Разрешение на уведомления
запрашивается лениво — при первом запуске отдыха, не при входе на
страницу. Надёжность разная по платформам: хорошо на Android/Chrome для
типичной длительности отдыха (60–180 сек), заметно менее надёжно на
iOS/Safari (агрессивно приостанавливает JS свёрнутых вкладок). Полностью
гарантированная работа на iOS потребовала бы Web Push с собственным
сервером (VAPID-ключи, хранение подписок, бэкенд, отправляющий push ровно
в момент окончания каждого таймера) — отдельная, более крупная задача,
не реализована.

  - Отдельно, когда дойдём — фирменный HTML-шаблон письма (подтверждение
