# ARCHITECTURE.md — техническая карта проекта DonatelleX

> Этот файл — не журнал решений (для этого есть `PROJECT_PLAN.md`), а
> структурная карта: что где лежит, как всё связано, зачем каждая часть
> существует. Цель — чтобы новый разработчик, открыв только этот файл,
> понял устройство всего проекта без необходимости читать весь код с нуля.
>
> Обновляется при каждой поставке файлов, если менялась структура/системы
> (не при каждой мелкой правке текста).

## 1. Что это за проект

DonatelleX — фитнес-платформа с персональными программами тренировок
(8 готовых программ: пол × цель [похудение/набор массы] × формат
[дом/зал], каждая на 24–48 недель). Состоит из трёх отдельных
веб-приложений в одном монорепозитории:

| Приложение | Для кого | Технически |
|---|---|---|
| `apps/web` | Конечные пользователи | PWA (прогрессивное веб-приложение) |
| `apps/admin` | Администратор/владелец | CMS — управление контентом, пользователями, платежами |
| `apps/landing` | Посетители сайта до регистрации | Маркетинговый сайт, 10 языков |

Все три — независимо развёрнутые Vercel-проекты, независимо
собираются и деплоятся, но используют **общую базу данных Supabase** и
**общие npm-пакеты** внутри монорепозитория.

## 2. Технологический стек

- **Frontend:** React 19 + Vite + TypeScript + Tailwind CSS
- **Роутинг:** react-router-dom
- **Данные и состояние сервера:** @tanstack/react-query (все обращения к
  Supabase идут через хуки на его основе — `useQuery`/`useMutation`)
- **Формы:** react-hook-form
- **Backend:** Supabase (Postgres + Auth + Storage + Edge Functions), без
  отдельного собственного бэкенда — вся бизнес-логика либо на клиенте,
  либо в SQL (функции/триггеры), либо в Edge Functions (`supabase/functions/`)
- **Монорепо:** pnpm workspaces + Turborepo (`turbo.json`, `pnpm-workspace.yaml`)
- **Локализация:** i18next + react-i18next (у каждого из трёх приложений
  свой независимый набор файлов переводов — они не шарятся)
- **PWA:** vite-plugin-pwa (у `apps/web` и `apps/landing`; `apps/admin` —
  обычное SPA, не PWA)

### Как приложения ссылаются друг на друга

- `apps/web` и `apps/admin` импортируют `@donatellox/types` (общие типы) —
  например `import type { WorkoutProgram } from "@donatellox/types"`
- `apps/web`, `apps/admin`, `apps/landing` — каждое использует
  `@donatellox/theme` для Tailwind-конфига (`tailwind.config.js` каждого
  приложения делает `import baseConfig from "@donatellox/theme/tailwind.config"`)
- Прямых импортов между `apps/*` НЕТ — они полностью независимы,
  связаны только через общую базу данных Supabase

## 4. База данных (Supabase/Postgres)

### 4.1 Основные таблицы и связи

```
users (профиль + роль: user/admin/superadmin)
  └─ user_profiles (анкета: пол, рост, вес, цели, дата рождения, активность)
  └─ subscriptions (доступ — см. 4.3, ВАЖНО про модель оплаты)
  └─ payments (лог платежей от провайдеров)
  └─ progress_entries (вес/замеры/фото пользователя со временем)
  └─ workout_logs (история пройденных тренировок)
  │     └─ total_volume_kg (суммарный поднятый вес за тренировку)
  │     └─ completed_sets (jsonb: что реально сделал по каждому упражнению)
  └─ user_achievements (разблокированные награды, см. 4.4)
  └─ calorie_overrides (ручное переопределение расхода калорий на день)
  └─ referral_code, pending_discount_percent (реферальная программа)

workout_programs (8 программ + любые новые, добавленные через конструктор)
  └─ gender, goal, training_format — по этим полям идёт подбор программы
  └─ title_en/es/hy, description_en/es/hy — переводы (см. раздел 8)
  └─ workouts (тренировки/дни программы)
        └─ week_order, week_label — группировка по неделям/месяцам
             (НЕ отдельная таблица — просто общее поле у нескольких workouts,
             см. раздел 4.2)
        └─ title_en/es/hy, week_label_en/es/hy — переводы
        └─ workout_sets (подходы: какое упражнение, сколько повторений,
             отдых, заметка)
              └─ exercise_id → exercises (общий каталог, не дублируется
                   на программу)
              └─ notes_en/es/hy — переводы

exercises (общий каталог упражнений, ~2040 штук, переиспользуется всеми
  программами — одно и то же упражнение может встречаться в нескольких
  программах через workout_sets.exercise_id)
  └─ video_url — ссылка на видео (см. раздел 9)
  └─ title_en/es/hy — переводы

achievements (каталог наград, см. 4.4) — справочник, не пользовательские данные
```

### 4.2 Важная идея: "недели" — не отдельная сущность

В `workout_programs` **нет** таблицы "weeks". Неделя/блок программы — это
просто общее значение `week_order` + `week_label` у нескольких строк
`workouts`. Чтобы добавить программе новый месяц тренировок — создаётся
просто ещё один `workouts` с новым `week_order`. Это осознанное решение
(см. `PROJECT_PLAN.md`, Фаза 7) — не плодить лишнюю сущность там, где
достаточно группировки по полю.

### 4.3 Модель оплаты — НЕ подписка с автосписанием

⚠️ Критично для любого, кто будет дописывать платежи (Фаза 3 ещё не
реализована — есть только приём вебхуков, `create-checkout` не написан):

`subscriptions` — по названию похоже на классическую подписку, но
**модель — разовая оплата за период**, без автопродления. Пользователь
платит один раз за месяц/квартал/год, `current_period_end` — просто дата,
когда доступ прекращается. Когда `create-checkout` будет писаться —
Stripe должен создаваться в режиме `mode: "payment"`, НЕ
`mode: "subscription"` — иначе будет реальное автосписание, а сайт
обещает пользователю, что его нет. Подробности и обоснование — в
`PROJECT_PLAN.md`, Фаза 3.

Особый случай — `provider = 'gift'`, `plan = 'lifetime'`: безлимитный
доступ, который выдаёт только админ вручную (кнопка в `UsersPage.tsx`
админки, RPC `grant_lifetime_access`/`revoke_lifetime_access`).
`current_period_end` для таких записей — не `'infinity'` (это ломает
JS `Date`, см. баг в Фазе 0), а `now() + 100 лет`.

### 4.4 Система наград — разблокировка на сервере, не на клиенте

`achievements` (каталог) + `user_achievements` (что разблокировано).
Разблокировка происходит **триггером в Postgres**
(`check_and_unlock_achievements()`) после каждой вставки в `workout_logs`
— не пересчитывается на клиенте при каждой загрузке экрана. Категории:
`workouts` (по числу тренировок), `streak` (серия дней подряд, считается
функцией `calculate_streak_days()`), `volume` (по суммарному поднятому
весу), `special`. Подробности — `PROJECT_PLAN.md`, Фазы 2.6/6.2.

### 4.5 RLS (Row Level Security)

Все таблицы защищены RLS-политиками (Postgres). Общий паттерн:
- Пользовательские данные (`workout_logs`, `progress_entries`,
  `subscriptions`, `payments` и т.д.) — `user_id = auth.uid() OR is_admin()`
- Справочники (`exercises`, `workout_programs`, `workouts`,
  `workout_sets`, `achievements`) — читать может любой авторизованный,
  **писать — только админ** (`*_write_admin` политики, используются
  конструктором программ в админке, см. раздел 6.3)
- `user_achievements` — читать только свои, писать может ТОЛЬКО триггер
  (security definer) — пользователь не может выдать себе награду напрямую

### 4.6 Полный список таблиц (по миграции создания)

См. раздел 7 (журнал миграций) — там же видно, в какой миграции что
появилось. Основные (0001): `users`, `user_profiles`, `exercises`,
`workout_programs`, `workouts`, `workout_sets`, `workout_logs`,
`progress_entries`, `subscriptions`, `payments`, `notifications`.
Добавленные позже: `achievements`, `user_achievements` (0023),
`calorie_overrides` (0025).

## 5. `apps/web` — PWA для пользователей

### 5.1 Точка входа и общая структура

- `main.tsx` — точка входа. Регистрирует `registerSW()` из
  `virtual:pwa-register` (иначе обновления PWA не подхватываются
  автоматически у уже открытых вкладок — см. баг в `PROJECT_PLAN.md`,
  Фаза 0), оборачивает приложение в `QueryClientProvider` → `BrowserRouter`
  → `AuthProvider`
- `App.tsx` — все маршруты. Основные страницы — внутри `AppShell`
  (нижняя навигация: Главная/Программы/Питание/Прогресс/Профиль).
  Полноэкранные без навигации — `/workout/:id`, `/achievements`,
  `/subscription` и авторизационные страницы
- `context/AuthContext.tsx` — обёртка над Supabase Auth, даёт
  `useAuth()` (текущий пользователь, методы входа/выхода) всему дереву

### 5.2 Ключевой файл — `lib/queries.ts`

Все обращения к Supabase из `apps/web` идут через хуки в этом файле —
единая точка данных, страницы сами Supabase почти не дёргают напрямую.
Основные хуки:

| Хук | Что делает |
|---|---|
| `useUserProfile()` | Анкета пользователя |
| `useActiveSubscription()` | Есть ли активный доступ (см. 4.3) |
| `usePrograms()` / `useRecommendedProgram()` | Список программ / подбор под пользователя по gender+goal+training_format |
| `useWorkoutHistory()` / `useWorkoutStats()` | История тренировок, стрик, суммарное число |
| `useAchievements()` | Каталог наград + статус разблокировки (сливает `achievements` и `user_achievements`) |
| `usePersonalRecords()` | Личные рекорды по весам — считается на клиенте из `workout_logs.completed_sets`, отдельной таблицы нет |
| `useVolumeStats()` | Поднятый вес по периодам (тренировка/неделя/месяц/год/всё время) |
| `useDailyCalories()` | Автоматическая оценка расхода калорий (формула в `lib/calories.ts`) + ручное переопределение |
| `useSetCalorieOverride()` / `useClearCalorieOverride()` | Ручной ввод калорий на день |
| `useFreeProgramAccess()` | Бесплатный пробный доступ к одной программе в первую неделю после регистрации |

### 5.3 Система доступа к программам (важная логика)

В `App.tsx` (`ProgramDetailPage`) и `ProgramsPage.tsx`:
```
isLocked = program.isPremium && !hasFreeAccess && !activeSubscription
```
Раньше здесь был критичный баг (программа была заблокирована ВСЕГДА,
независимо от подписки) — см. `PROJECT_PLAN.md`, Фаза 0. Эта формула —
контракт, который нельзя менять не глядя на обе стороны (и бесплатный
период, и настоящую подписку).

### 5.3.1 Последовательное открытие тренировок (не путать с 5.3 выше)

Отдельная от премиум-пейволла система — `isLocked` (5.3) решает "может
ли пользователь вообще заниматься по этой программе", а это — "в каком
порядке ему можно проходить тренировки внутри неё". Обе проверки
применяются независимо, в `ProgramDetailPage`.

Никакого отдельного "указателя прогресса" в базе нет — вычисляется на
лету из уже существующих данных:
1. `completedWorkoutIds` — какие `workout_id` этой программы уже есть в
   `workout_logs` у текущего пользователя (`useQuery`, ключ
   `["completed-workout-ids", program.id, session.user.id, workouts.length]`)
2. `nextUnlockedWorkoutId` — первая в каноническом порядке
   (`week_order → order`, тот же порядок, каким и запрашиваются
   `workouts`) тренировка, которой ещё нет в `completedWorkoutIds`

Порядок глобальный по всей программе — не сбрасывается по неделям и не
зависит от календаря (месяц пропуска зала не "разблокирует" следующую
тренировку саму по себе, только реальное выполнение предыдущей). Список
недели (`visibleWorkouts`, переключается вкладками) показывает ВСЕ
тренировки выбранной недели, но у каждой своё из трёх состояний:
пройдено / доступно сейчас / заблокировано (замок, не кликается — рендерится
как обычный `<div>`, не `<Link>`).

**Догнать реальный прогресс** — у каждой заблокированной тренировки есть
кнопка "Уже занимался(-ась) раньше?" (`catchUpMutation`). Решает случай,
когда у пользователя есть реальный прогресс, не отражённый в
`workout_logs` (занимался по программе до появления приложения/этой
функции — не редкость для новых клиентов, переходящих с бумажных
программ). По подтверждению — батч-insert в `workout_logs` для выбранной
тренировки и всех канонически идущих до неё, без детального
`completed_sets` (только факт "пройдено", этого достаточно для логики
разблокировки).

⚠️ Не реализовано (сознательно, программы пока идут только на месяц —
"дальше будем добавлять продолжение"): что показывать по завершении ВСЕЙ
программы целиком.

### 5.4 Локализация контента программ (не только интерфейса)

Помимо обычного i18next (интерфейс — кнопки/заголовки, `i18n/locales/`,
языки ru/en полностью + остальные 8 через fallback на en), у программ
тренировок отдельная система перевода САМОГО КОНТЕНТА (названия
упражнений, тренировок, заметки тренера) — она не через i18next, а через
колонки `*_en`/`*_es`/`*_hy` прямо в таблицах БД (см. раздел 4.1) и
функцию `lib/localizedField.ts`:

```ts
localizedField(program.title, { en: program.titleEn, es: program.titleEs, hy: program.titleHy }, i18n.language)
```

Используется в `App.tsx`, `ProgramsPage.tsx`, `WorkoutPlayerPage.tsx`,
`DashboardPage.tsx`, `queries.ts` (`usePersonalRecords`) — везде, где
показывается текст программы/упражнения. Подробности архитектуры и как
переводился контент (словарный движок, не построчный вручную) —
`PROJECT_PLAN.md`, Фаза 6.

### 5.5 `WorkoutPlayerPage.tsx` — сама тренировка

Самая сложная страница. Отвечает за:
- Отметку подходов выполненными, ввод рабочего веса
- **Таймер отдыха** между подходами (`set.restSeconds`) и отдельно между
  упражнениями для зальных программ (`REST_BETWEEN_EXERCISES_SECONDS = 180`,
  только если `workout.trainingFormat === "gym"`) — блокирует отметку
  следующего подхода, пока идёт отдых
- Подсчёт `total_volume_kg` при сохранении тренировки (вес × повторения
  по всем подходам) — считается на клиенте здесь, т.к. только тут есть
  все данные разом
- **Универсальный видеоплеер** (`lib/video.ts`, `getYouTubeEmbedUrl()`) —
  понимает и прямые ссылки на файлы, и YouTube, с анимированным
  открытием/закрытием модалки (см. раздел 9)
- **Подтверждение выхода** — если хотя бы один подход уже отмечен, кнопка
  "Назад" сначала спрашивает подтверждение, не выходит сразу
- **Переставить/заменить упражнение** — оба только на текущий сеанс
  (клиентское состояние `orderOverride`/`substitutions`, программу в базе
  не меняют). При сохранении тренировки в историю пишется ID реально
  выполненного (заменённого, если была замена) упражнения — иначе личные
  рекорды/объём задваивались бы неправильному движению

### 5.6 Питание (`NutritionPage.tsx`)

Автоматический расчёт расхода калорий (формула Миффлина-Сан Жеора,
`lib/calories.ts`) — НЕ ручной дневник еды (была более ранняя версия с
дневником, заменена — см. `PROJECT_PLAN.md`, миграция 0025). Плюс
статичные рекомендации по БЖУ под цель пользователя.

## 6. `apps/admin` — CMS

### 6.1 Структура

`App.tsx` — маршруты за `RequireAdmin` (проверяет роль admin/superadmin)
внутри `AdminShell` (боковая навигация). Страницы: `OverviewPage`,
`UsersPage`, `ProgramsPage` → `ProgramDetailPage`, `VideosPage`,
`PaymentsPage`.

### 6.2 `VideosPage.tsx` — управление видео упражнений

Список всех упражнений каталога (общий для всех программ). Клик по
карточке открывает форму **редактирования существующего** упражнения
(update, не insert) — можно прикрепить/поменять ссылку на видео,
изменить сложность/группы мышц. Отдельная кнопка "Новое упражнение" —
для создания с нуля (редкий случай). Счётчик "видео прикреплено: N из
total" + фильтр "только без видео".

### 6.2.1 `SettingsPage.tsx` — настройки сайта (`/settings`)

Редактирует `site_settings` (общая key-value таблица, БД, не переменные
окружения) — применяется на лендинге сразу, без редеплоя. Список полей
вынесен в массив `SETTINGS_FIELDS` в начале файла — новая настройка в
будущем добавляется туда, не переписыванием формы. Два поля на сегодня:
- `hero_background_video_url` — фоновое видео на весь экран Hero (прямая
  ссылка на файл, YouTube не подходит — нет прямого файла)
- `hero_showreel_url_ru`/`en`/`es`/`hy` — ролик для кнопки "Узнать
  больше", отдельная ссылка под каждый язык, выбирается на лендинге по
  текущему `i18n.language`, с запасным вариантом на русский

### 6.3 `ProgramDetailPage.tsx` — конструктор программ

Самый большой файл в админке. Открывается по клику на карточку программы
(`/programs/:programId`). Полный CRUD:
- Редактирование программы целиком (название/описание/цель/сложность/
  число недель/премиум)
- Недельные блоки — вкладки, переключение, добавление НОВОГО блока
  (создаёт первую тренировку с новым `week_order` — см. раздел 4.2)
- Тренировки внутри блока — добавить/редактировать/удалить/переместить
  вверх-вниз (`useReorderWorkout` — меняет `order` через временное
  значение, чтобы избежать коллизий)
- Упражнения внутри тренировки — добавить из каталога (поиск) или
  создать новое, редактировать (два независимых слоя: само упражнение —
  общее на весь каталог, с предупреждением в UI; и подходы именно в этой
  тренировке — реализовано как "удалить всё и вставить заново", не
  построчный diff), убрать из тренировки
- **Безопасное удаление тренировки** — сначала проверка `workout_logs`
  (не потеряет ли пользователь историю), блокирует удаление с понятным
  сообщением, если да

Все мутации — локальные хуки в начале файла (`useSaveWorkout`,
`useDeleteWorkout`, `useAddExerciseToWorkout`, `useSaveExerciseSets` и
т.д.), не вынесены в общий `queries.ts` (в отличие от `apps/web` — в
`apps/admin` так исторически не сложилось, у каждой страницы свои хуки
инлайн).

## 7. `apps/landing` — маркетинговый сайт

⚠️ С Фазы 13 лендинг больше не полностью статический — единственное
обращение к базе: `lib/supabase.ts` (клиент без сохранения сессии, ни
логина, ни личного кабинета на лендинге нет и не планируется) читает
`site_settings` (см. 6.2.1) для настроек вроде ссылки на видео-ролик.
Требует `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` в окружении Vercel-
проекта лендинга (те же значения, что у `apps/web`) — без них сборка
пройдёт, но открытая страница будет падать в браузере на попытке чтения.

### 7.1 Структура

`App.tsx` — три маршрута (`/`, `/terms`, `/privacy`). Главная собрана из
секций в `sections/`: `Hero` + `HeroMobileDetails` (второй экспорт из
того же `Hero.tsx` — чек-лист/вторая кнопка/соц.доказательство, убранные
с первого экрана на мобильном, видны только там, `lg:hidden`; на
десктопе всё внутри самого `Hero`, этот компонент не рендерится), `Pricing`
(сразу после Hero — было дальше по странице, поднято выше: друзья
пользователя на мобильном не сразу находили путь до цен, ссылка в шапке
спрятана за гамбургер-меню), `ForWomenMen`
("Для женщин"/"Для мужчин", двухколоночный блок с тегами-особенностями
каждой аудитории), `Modules` ("Возможности"), `WeeklyPlan` ("Твой план"),
`Steps` ("Как начать"), `Faq`, `CallToAction`.

### 7.1.1 Шрифты — единственное место загрузки

Все шрифты сайта грузятся из одного места: `packages/theme/src/fonts.css`
(подключается через `@import "@donatellox/theme/fonts.css";` в начале
`index.css` каждого из трёх приложений) — единственный `<link>`/`@import`
на Google Fonts во всём проекте, специально не дублируется больше нигде.

- `Manrope` — покрывает Latin+Cyrillic, используется и для обычного текста
  (`--font-body`), и для заголовков (`--font-display`/Tailwind-класс
  `.font-display`, читает `fontFamily.display` из `tokens.ts`)
- `Noto Sans Arabic/Armenian/Devanagari/Gurmukhi` — Manrope не покрывает
  эти письменности, поэтому для армянского/арабского/хинди/панджаби
  (используются на лендинге, где реально все 10 языков) — отдельные
  шрифты тем же способом
- Жирность заголовков (800) задаётся **централизованно один раз** —
  `.font-display { font-weight: 800; }` в `fonts.css`, а не на каждом
  компоненте — Manrope, в отличие от однонасыщенных display-шрифтов,
  не выглядит "жирным" по умолчанию без явного указания

При добавлении нового шрифта — редактировать только `fonts.css` (сам
`@import` и переменные `--font-body`/`--font-display`), `tokens.ts`
(`fontFamily.display`/`.body` — список для Tailwind-классов
`font-display`/`font-body`) должен зеркалировать те же названия семейств.
`<link>`-теги в `index.html` для этого не нужны и не используются — если
где-то появятся снова, это дублирование, а не альтернативный способ.

### 7.2 Локализация — здесь ПОЛНОСТЬЮ 10 языков

В отличие от `apps/web` (только ru+en полностью, остальные через
fallback), лендинг переведён на все 10 языков с самого начала (Фаза 1).
При добавлении новых секций/текста — переводить нужно на все 10 сразу,
иначе будет разнобой (это уже случалось один раз при редизайне
FAQ/Steps/CTA — пришлось досоздавать для 8 отставших языков).

### 7.3 Регион и цены (`context/RegionContext.tsx`, `lib/regionPricing.ts`)

Определяет регион посетителя (Россия/Европа/США), показывает цены и
способы оплаты под регион, модалка выбора при первом визите
(`RegionSwitcher.tsx`). `regionPricing.ts` — таблицы цен, `PurchasablePlan`
(тип, исключающий `'lifetime'` — этот план не продаётся, только дарится
через админку).

### 7.4 Exit-intent модалка (`hooks/useExitIntent.ts`, `components/ExitIntentModal.tsx`)

Показывается один раз за сессию (sessionStorage), когда курсор уходит
вверх за пределы страницы (десктоп; на мобильных не реализовано —
осознанно, чтобы не хватать браузер за руку через кнопку "назад").
Минимальная задержка 8 сек, прежде чем можно сработать. Офер — тот же,
что и везде на сайте (первая неделя бесплатно, без оплаты), не отдельная
скидка — см. рассуждение в истории чата и `PROJECT_PLAN.md`.

## 8. Локализация контента программ — сводка (подробности в PROJECT_PLAN.md)

Два независимых слоя перевода в проекте:

1. **Интерфейс** (кнопки, заголовки, статические тексты) — обычный
   i18next, файлы `apps/*/src/i18n/locales/*.json`
2. **Контент программ** (названия упражнений/тренировок, заметки
   тренера) — НЕ через i18next, а через колонки `title_en`/`title_es`/
   `title_hy` и т.д. прямо в таблицах БД (`exercises`, `workout_programs`,
   `workouts`, `workout_sets`) + функция `lib/localizedField.ts` на
   клиенте. Переведено словарным движком (Python-скрипты, не хранятся в
   репозитории — были во временной рабочей папке при генерации),
   переводы залиты SQL-миграциями `0029-0058`. Языки: en, es, hy.
   Остальные 7 языков лендинга НЕ имеют перевода контента программ (сам
   `apps/web` для них тоже не переведён — они через fallback на en).

## 9. Видео упражнений

`exercises.video_url` — одна ссылка на упражнение (не файл, а именно
ссылка — сами видео нигде в проекте не хранятся). Плеер
(`apps/web/src/lib/video.ts`, `getYouTubeEmbedUrl()`) понимает два
формата:
- Прямая ссылка на файл (mp4 и т.п.) — рендерится как `<video src=...>`
- YouTube-ссылка (любой формат: watch/embed/youtu.be/shorts) —
  определяется по regex, рендерится как `<iframe>` через
  `youtube-nocookie.com` с `modestbranding=1&rel=0`

Рекомендованный способ хостинга собственных видео — Cloudflare R2 или
Bunny Storage (не Supabase Storage — там платный egress-трафик, невыгодно
для видео). Подробное обоснование — в истории чата/PROJECT_PLAN.md.
